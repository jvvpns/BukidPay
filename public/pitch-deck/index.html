“THAT’S BUKIDPAY.” The organizer defines the event allocation in advance. When the participant pays, Paiflow automatically divides the registration into the predefined event allocations.

The guide sample uses a 20-person plan: two guides at about ₱1,200 each, or ₱120 per participant—7.5% of ₱1,600.

The 47.5% operations bucket covers event delivery costs and organizer earnings. The organizer’s actual profit is what remains after those costs.

Paiflow executes the configured Split. BukidPay confirms only after the allocation is verified.

Q&A 01 / 04

EXPECTED Q&A

Registration confirmation requires exact evidence

BukidPay checks the original transaction and the Paiflow events from that same payment.

01 FINALITY

The original transaction reaches SUCCESS on Stellar Testnet.

02 RECEIVE EVENT

One event matches the payer, native XLM, and 100000000 stroops.

03 EXACT SPLIT

One payout matches all four configured recipients at 750 / 1,500 / 3,000 / 4,750 bps.

✓ CONFIRM

10 XLM received and 10 XLM allocated. Only then does registration confirm.

SHORT ANSWER: BukidPay does not trust a success screen by itself. It checks final transaction success, the matching Receive event, and the exact configured four-recipient Split. Registration confirms only when the original 10 XLM is fully accounted for.

Q&A 02 / 04

EXPECTED Q&A

Uncertain status never creates a second payment

BukidPay retains the original evidence and keeps every recovery action tied to it.

PENDING UNKNOWN NOT_FOUND EXPIRED PREPARATION
RETAIN Original transaction hash
Exact signed envelope Preparation scope and correlation metadata stay attached
01Check the original transaction
02Retry only the exact signed envelope when appropriate
NO REPLACEMENT PREPARATION FROM AN UNCERTAIN RESULT

SHORT ANSWER: BukidPay saves the preparation before signing and the exact signed envelope before submission. A pending, unknown, missing, or expired result never authorizes a replacement. We check the original hash and retry only that same envelope when appropriate.

Q&A 03 / 04

EXPECTED Q&A

Prototype scope and production requirements

WORKING PROTOTYPE

What exists today

  • Stellar Testnet payment authorized through Freighter
  • One configured native XLM Paiflow Receive and Split deployment
  • Exact transaction and allocation verification before confirmation
  • Browser recovery that preserves the original payment evidence
BEFORE PRODUCTION

What the real service still needs

  • User authentication and registration ownership checks
  • Durable order and recovery storage across devices
  • Shared rate limits and operational monitoring
  • Trusted pricing, production payment rails, and legal review
₱1,600 is the actual event registration. 10 XLM is the Testnet demo and has no real monetary value.

SHORT ANSWER: This is a Testnet prototype of the payment lifecycle, not a production checkout or fiat conversion service. The payment and verification flow works, while a real service still needs authentication, durable storage, shared controls, trusted pricing, and legal review.
